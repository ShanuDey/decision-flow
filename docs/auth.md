# Authentication

Every API route except `/health` and `/ready` requires a bearer token. There is no switch to turn this off. If no provider is configured, the API refuses to start.

```
Authorization: Bearer <token>
```

The API only verifies tokens. It never stores passwords and never shows a login page. A token comes from an identity provider you configure, and the API checks its signature, issuer, audience and expiry.

## Configure providers

`AUTH_PROVIDERS` is a JSON list. Each entry is one of two types.

### `jwt`: signed tokens

Works with any provider that issues signed JWTs (Google, Firebase, Neon Auth, Auth0, Keycloak, Entra, Okta, or your own web server).

| Field | Meaning |
|---|---|
| `name` | Unique label, returned as `provider` by `GET /me` |
| `issuer` | The token's `iss` claim |
| `audience` | The token's `aud` claim (your client id or project id) |
| `jwks_url` | Where the provider publishes its keys. Leave empty to discover it from the issuer's OIDC metadata |
| `public_key` | A PEM public key, instead of `jwks_url`. `\n` escapes are allowed. Set one of the two, not both |
| `algorithms` | Allowed signature algorithms (default `RS256`, `ES256`). Symmetric algorithms and `none` are never accepted |

Examples:

```json
[
  {"type": "jwt", "name": "google", "issuer": "https://accounts.google.com",
   "audience": "<google-client-id>"},
  {"type": "jwt", "name": "firebase",
   "issuer": "https://securetoken.google.com/<project-id>", "audience": "<project-id>",
   "jwks_url": "https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com"},
  {"type": "jwt", "name": "keycloak", "issuer": "https://sso.example.com/realms/acme",
   "audience": "decision-flow"}
]
```

For Neon Auth, use the issuer, audience and JWKS URL shown in your Neon project's auth settings.

### `userinfo`: opaque tokens

For providers that issue opaque tokens instead of JWTs (GitHub). The API sends the token to the provider's user endpoint and uses the answer.

```json
{"type": "userinfo", "name": "github", "userinfo_url": "https://api.github.com/user",
 "subject_field": "id", "name_field": "login"}
```

A userinfo provider cannot check which application a token was issued for, so use it only with your own first-party app. A JWT is never sent to a userinfo endpoint.

### Several providers

The API tries `jwt` providers first, then `userinfo` ones. A client can name one with the `X-Auth-Provider` header, which avoids trying the others.

## Restrict by email domain

```
AUTH_ALLOWED_EMAIL_DOMAINS=example.com,partner.org
```

Only tokens with a **verified** email in one of these domains are accepted; anything else gets `403`. Userinfo providers never report a verified email, so the domain rule rejects them.

## Web sign-in

The web app signs people in and is the only public entry point. Browsers talk to the web server, which checks the session, signs a short-lived (5 minute) token with its private key, and forwards the call to the API. The API only needs the matching public key (the `web` entry in `AUTH_PROVIDERS`). Browsers never see the API address or the token.

```
Browser ── cookie ──► web (Next.js) ── Bearer token ──► API
                         │
                         └─► Postgres, schema "auth" (users, sessions)
```

Users and sessions live in an `auth` schema of the same Postgres database. The web server creates and migrates that schema itself at start (set `AUTH_AUTO_MIGRATE=false` to do it yourself). The API does not read it, and Alembic ignores it.

### Login methods

`AUTH_METHODS` lists the login methods, comma-separated. Unset means password only.

```
AUTH_METHODS=password,github,google
```

- `password` is email and password.
- Any other name is a social provider that Better Auth supports (`github`, `google`, `discord`, `microsoft` and more; see Better Auth's docs for the full list and each provider's options).
- For a method `NAME`, every variable `NAME_<OPTION>` is passed to that provider as an option, with the option name in camelCase: `GITHUB_CLIENT_ID` becomes `clientId`, `COGNITO_USER_POOL_ID` becomes `userPoolId`. Usually that is just `NAME_CLIENT_ID` and `NAME_CLIENT_SECRET`; the provider's Better Auth docs list anything else. Only text options are supported.
- The app does not check these at start. A mistake appears in the **web server log** (search for `[Better Auth]`) when someone clicks the button. See "After you deploy" below.
- The login page shows exactly the listed methods. For a public deployment, leave `password` out.
- A social login never attaches to an existing account because the emails match, and a failed provider login returns to the login page with a short message.

Other variables:

| Variable | Meaning |
|---|---|
| `BETTER_AUTH_SECRET` | Random secret for sessions (generated by `make auth-setup`) |
| `BETTER_AUTH_URL` | Public URL of the web app; also the token issuer unless `AUTH_TOKEN_ISSUER` is set. It must equal the `issuer` of the `web` entry in `AUTH_PROVIDERS` |
| `AUTH_TOKEN_AUDIENCE` | Token audience (default `decision-flow-api`); must equal the provider's `audience` |
| `AUTH_SIGNING_KEY` | Private key that signs API tokens. Keep it secret |
| `AUTH_DATABASE_URL` | Optional. Where the `auth` schema lives. Left unset, the web server uses `DATABASE_URL` (its Python driver prefix removed). Set it when the web runs apart from the API, to use a pooled connection string on serverless, or a role limited to that schema |
| `API_URL` | Server-only address the web server uses to reach the API |
| `AUTH_TRUSTED_ORIGINS` | Extra origins allowed to make write requests, comma-separated (for example a preview URL that differs from `BETTER_AUTH_URL`) |
| `AUTH_ALLOWED_EMAIL_DOMAINS` | Only verified emails from these domains may sign up with Google or GitHub. Set the same value on the API so it also checks tokens |
| `AUTH_IP_HEADER`, `AUTH_TRUSTED_PROXIES` | Where the sign-in rate limit reads the client IP (default `x-forwarded-for`). Name a header your proxy overwrites, since any client can send the default one when the web server is exposed directly. `AUTH_TRUSTED_PROXIES` lists proxy IPs or CIDRs |
| `AUTH_AUTO_MIGRATE` | `false` stops the web server migrating the `auth` schema at start; run `make auth-migrate` yourself |

### Email and password

Password accounts are created only by the server: set `AUTH_ADMIN_EMAIL` and `AUTH_ADMIN_PASSWORD`, and the admin is created at start when no user exists (its email counts as verified). Public sign-up is always closed, so a visitor cannot create a password account. `make auth-setup` fills these in for local work with a random password in your `.env`. Do not set them on a public deployment; use Google or GitHub there.

Sign-in attempts are rate limited per instance (10 a minute for the password form). The limit is held in memory, so it is per server process.

### Google and GitHub

Register an OAuth app with the provider and set the redirect URL to `<BETTER_AUTH_URL>/api/auth/callback/<name>`, for example `http://localhost:3000/api/auth/callback/github` locally. Put the client id and secret in `<NAME>_CLIENT_ID` and `<NAME>_CLIENT_SECRET`. In Docker, add them to the `app` service in the compose file, since compose passes only the variables it lists. Anyone with an account at the provider can then sign in, so pair a public deployment with limits (see the deployment notes), or restrict sign-up with `AUTH_ALLOWED_EMAIL_DOMAINS`.

### After you deploy

Better Auth reports a bad provider setup when it is used, so check each login method once after a deploy. Look in the web server's log (container logs, or the platform's function logs), not the browser console and not the API log.

1. `/health` returns 200, and `/login` shows the buttons you listed.
2. For each social method, ask Better Auth to start the sign-in. A good setup answers with the provider's address. A missing client id, a misspelled name or missing options answers with an empty HTTP 500, and the web server log says why:

   ```
   curl -s -X POST https://<web-url>/api/auth/sign-in/social \
     -H "Content-Type: application/json" -H "Origin: https://<web-url>" \
     -d '{"provider":"github","callbackURL":"/flows"}'
   ```

3. Sign in with each provider once. A wrong or missing client secret only fails here, when the provider is asked to exchange the code.

## Local development

`make start` runs `make auth-setup`, which appends to your untracked `.env`: a freshly generated key pair, the web session secret, the database URL for the `auth` schema, and a local admin account (see `AUTH_ADMIN_EMAIL` and `AUTH_ADMIN_PASSWORD` in `.env`). Each machine gets its own values; nothing is shared or committed. Open `http://localhost:3000` and sign in with that admin.

To call the API by hand:

```
curl -H "Authorization: Bearer $(make -s auth-token)" http://localhost:8000/me
```

## Responses

| Status | Meaning |
|---|---|
| `401 unauthenticated` | Missing, malformed, expired or unknown token. Includes `WWW-Authenticate: Bearer` |
| `403 forbidden_domain` | Valid token, but the email domain is not allowed |
| `503 auth_unavailable` | The identity provider could not be reached |

`GET /me` returns the authenticated caller (`sub`, `provider`, `email`, `name`).

## Interactive docs

`/docs`, `/redoc` and `/openapi.json` list every endpoint, so they are off by default. Set `API_DOCS_ENABLED=true` to serve them for local work, and leave it unset when deployed.

## Security notes

- Treat the backend URL as public. Every request is checked, so knowing the URL gives no access beyond `/health` and `/ready`. Only the web URL needs to be published.
- Keep signing keys and client secrets in your platform's secret store, never in the repository.
- The single Docker image runs the API and the web in one container, so the API process can see `AUTH_SIGNING_KEY` although it only needs the public key. Run them as separate services to avoid that.
- If every call returns `401`, check that the `issuer` and `audience` of the `web` entry in `AUTH_PROVIDERS` equal `BETTER_AUTH_URL` (or `AUTH_TOKEN_ISSUER`) and `AUTH_TOKEN_AUDIENCE`. The API logs the reason for each rejected token at INFO level.
